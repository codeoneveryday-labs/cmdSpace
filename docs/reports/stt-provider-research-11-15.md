# STT Provider Research: 11-15

Research date: 2026-08-11. Scope: official primary documentation only.

This report captures the speech-to-text integration surface for providers 11-15:
Groq, Inworld AI, Rev AI, Verbit, and Nuance.

## Summary

- Groq: synchronous HTTP only in the docs reviewed; OpenAI-compatible multipart upload.
- Inworld AI: synchronous HTTP plus bidirectional WebSocket streaming.
- Rev AI: asynchronous job API plus WebSocket/RTMP streaming.
- Verbit: post-production async APIs plus live streaming/session APIs.
- Nuance: ASRaaS gRPC streaming with OAuth2 client-credentials flow and Mix credentials.

## 11. Groq

- **Auth mechanism.** Groq uses an API key in `Authorization: Bearer $GROQ_API_KEY`; the quickstart recommends putting the key in `GROQ_API_KEY` and the API reference repeats the bearer pattern. Sources: [Groq Quickstart](https://console.groq.com/docs/quickstart), [Groq API Reference](https://console.groq.com/docs/api-reference).
- **Base endpoint.** STT transcription uses `POST https://api.groq.com/openai/v1/audio/transcriptions`; translation uses `POST https://api.groq.com/openai/v1/audio/translations`. Sources: [Groq Speech to Text](https://console.groq.com/docs/speech-to-text), [Groq API Reference](https://console.groq.com/docs/api-reference).
- **Sync / async / stream protocol.** The docs I reviewed document synchronous HTTP POST transcription/translation only. I did not find a Groq STT streaming or async job endpoint in the official STT pages reviewed. Sources: [Groq Speech to Text](https://console.groq.com/docs/speech-to-text), [Groq API Reference](https://console.groq.com/docs/api-reference).
- **Request encoding.** The transcribe endpoint accepts multipart form data with `file` or `url`, plus `model` and optional `prompt`, `language`, `response_format`, `temperature`, and `timestamp_granularities[]`. The docs also note supported file types and size limits. Sources: [Groq API Reference](https://console.groq.com/docs/api-reference), [Groq Speech to Text](https://console.groq.com/docs/speech-to-text).
- **Response text path.** The transcription response text is in the top-level `text` field. When `response_format=verbose_json`, the response adds segment metadata. Sources: [Groq API Reference](https://console.groq.com/docs/api-reference), [Groq Speech to Text](https://console.groq.com/docs/speech-to-text).
- **Credential / settings requirements.** The docs call out `whisper-large-v3` and `whisper-large-v3-turbo`, audio file limits of 25 MB free tier / 100 MB dev tier, and a recommendation to use 16 kHz mono audio. `response_format` must be `verbose_json` to use timestamp granularities. Sources: [Groq Speech to Text](https://console.groq.com/docs/speech-to-text), [Groq Whisper Large v3](https://console.groq.com/docs/model/whisper-large-v3).

## 12. Inworld AI

- **Auth mechanism.** Inworld requires an API key in the `Authorization` header. The docs use the form `Authorization: Basic $INWORLD_API_KEY` for server-side requests; the API introduction also documents JWT bearer auth for browser/WebRTC scenarios. Sources: [Inworld API Introduction](https://docs.inworld.ai/api-reference/introduction), [Inworld STT Transcribe](https://docs.inworld.ai/api-reference/sttAPI/speechtotext/transcribe), [Inworld STT WebSocket](https://docs.inworld.ai/api-reference/sttAPI/speechtotext/transcribe-stream-websocket).
- **Base endpoint.** Synchronous STT: `https://api.inworld.ai/stt/v1/transcribe`. Streaming STT: `wss://api.inworld.ai/stt/v1/transcribe:streamBidirectional`. The docs also summarize the STT API as a single endpoint with sync + WebSocket support. Sources: [Inworld STT Quickstart](https://docs.inworld.ai/stt/quickstart), [Inworld STT Transcribe](https://docs.inworld.ai/api-reference/sttAPI/speechtotext/transcribe), [Inworld STT WebSocket](https://docs.inworld.ai/api-reference/sttAPI/speechtotext/transcribe-stream-websocket).
- **Sync / async / stream protocol.** The docs reviewed document synchronous HTTP POST transcription and bidirectional WebSocket streaming. I did not find a separate async job queue for STT in the reviewed pages. Sources: [Inworld STT Overview](https://docs.inworld.ai/stt/overview), [Inworld STT Transcribe](https://docs.inworld.ai/api-reference/sttAPI/speechtotext/transcribe), [Inworld STT WebSocket](https://docs.inworld.ai/api-reference/sttAPI/speechtotext/transcribe-stream-websocket).
- **Request encoding.** Sync requests send JSON with `transcribeConfig` plus `audioData.content`, where the audio bytes are base64-encoded. Streaming requests send a first `transcribeConfig` message, then `audioChunk` messages with raw audio bytes, followed by optional `endTurn` and `closeStream`. Sources: [Inworld STT Quickstart](https://docs.inworld.ai/stt/quickstart), [Inworld STT Transcribe](https://docs.inworld.ai/api-reference/sttAPI/speechtotext/transcribe), [Inworld STT WebSocket](https://docs.inworld.ai/api-reference/sttAPI/speechtotext/transcribe-stream-websocket).
- **Response text path.** Sync responses expose text at `transcription.transcript`. Streaming responses wrap the transcript under `result.transcription.transcript`; usage is under `result.usage`. Sources: [Inworld STT Transcribe](https://docs.inworld.ai/api-reference/sttAPI/speechtotext/transcribe), [Inworld STT WebSocket](https://docs.inworld.ai/api-reference/sttAPI/speechtotext/transcribe-stream-websocket).
- **Credential / settings requirements.** The STT docs say to create an Inworld account, generate an API key in the Portal, and store the API credential safely. The request also needs model selection (`inworld/inworld-stt-1` in the docs), audio format such as `LINEAR16`, and commonly `sampleRateHertz`/`language`. Sources: [Inworld API Introduction](https://docs.inworld.ai/api-reference/introduction), [Inworld STT Quickstart](https://docs.inworld.ai/stt/quickstart), [Inworld STT Transcribe](https://docs.inworld.ai/api-reference/sttAPI/speechtotext/transcribe).

## 13. Rev AI

- **Auth mechanism.** Rev AI uses a bearer access token in `Authorization: Bearer <REVAI_ACCESS_TOKEN>`. The get-started guide says to generate the access token from the Rev AI account page. Sources: [Rev AI Get Started](https://docs.rev.ai/get-started), [Rev AI Asynchronous Get Started](https://docs.rev.ai/api/asynchronous/get-started), [Rev AI Streaming Overview](https://docs.rev.ai/api/streaming).
- **Base endpoint.** Default async STT base URL is `https://api.rev.ai/speechtotext/v1/`; the docs also document a streaming WebSocket endpoint at `wss://api.rev.ai/speechtotext/v1/stream`. Rev AI additionally documents regional deployment URLs such as `https://ec1.api.rev.ai/speechtotext/v1/` for EU. Sources: [Rev AI Asynchronous Overview](https://docs.rev.ai/api/asynchronous), [Rev AI Streaming Overview](https://docs.rev.ai/api/streaming), [Rev AI Global Deployments](https://docs.rev.ai/api/global-deployments).
- **Sync / async / stream protocol.** Rev AI documents asynchronous job submission plus polling/webhooks, and a separate streaming WebSocket API. I did not find a synchronous one-shot transcription endpoint in the docs reviewed. Sources: [Rev AI Get Started](https://docs.rev.ai/get-started), [Rev AI Asynchronous Overview](https://docs.rev.ai/api/asynchronous), [Rev AI Streaming Overview](https://docs.rev.ai/api/streaming).
- **Request encoding.** Async submission supports `application/json` or `multipart/form-data`; JSON is preferred and uses `source_config.url`, while multipart can upload a local file directly. Streaming requests use the `content_type` query parameter, with `audio/x-raw` or `audio/x-flac`; raw audio must be `S16LE` and include a sample rate. Sources: [Rev AI File Submission](https://docs.rev.ai/api/asynchronous/files), [Rev AI Streaming Requests](https://docs.rev.ai/api/streaming/requests), [Rev AI Streaming Overview](https://docs.rev.ai/api/streaming).
- **Response text path.** For async jobs, the transcript JSON is returned from `/jobs/{id}/transcript`; the plain-text alternative is available with `Accept: text/plain`. In the JSON transcript, text appears inside `monologues[].elements[].value`. Streaming transcript responses are serialized JSON text messages. Sources: [Rev AI Get Started](https://docs.rev.ai/get-started), [Rev AI Streaming Responses](https://docs.rev.ai/api/streaming/responses), [Rev AI Streaming Example Session](https://docs.rev.ai/api/streaming/example-session).
- **Credential / settings requirements.** Rev AI docs limit access tokens to a maximum of two at a time, document `delete_after_seconds` for job retention, and note that async jobs default to English if language is omitted. Sources: [Rev AI Get Started](https://docs.rev.ai/get-started), [Rev AI File Submission](https://docs.rev.ai/api/asynchronous/files), [Rev AI Asynchronous Submit Job](https://docs.rev.ai/api/asynchronous/reference/jobs/submittranscriptionjob.md).

## 14. Verbit

- **Auth mechanism.** Verbit uses different auth depending on the API surface. The Post-Production API supports API token auth (`Authorization: ApiToken <KEY>` or `api_token=<KEY>`) and OAuth 2.0 bearer auth. The live transcription/captioning docs use a JWT bearer token minted from an API key via `https://users.verbit.co/api/v1/auth`, and the WebSocket connection docs also show the short-lived customer-level token in `Authorization`. Sources: [Verbit Post-Production API](https://verbit.readme.io/docs/post-production-api), [Verbit Authentication](https://verbit.readme.io/docs/authentication), [Verbit WebSocket Connection](https://verbit.readme.io/docs/websocket-protocol).
- **Base endpoint.** Post-Production API: `https://api.verbit.co/api/` (US), `https://eu.api.verbit.co/api/` (EU), and `https://sandbox-api.verbit.co/api/`. Live WebSocket base URL: `wss://speech.verbit.co/ws`. Sources: [Verbit Post-Production API](https://verbit.readme.io/docs/post-production-api), [Verbit WebSocket Connection](https://verbit.readme.io/docs/websocket-protocol).
- **Sync / async / stream protocol.** The post-production surface is asynchronous job-based API work. Live booking supports booked live sessions, and the live session docs say ad-hoc sessions use WebSocket only. The WebSocket docs also note that if media is streamed by another protocol such as RTMP, WebSocket is only used for responses and flow-control. Sources: [Verbit Post-Production API](https://verbit.readme.io/docs/post-production-api), [Verbit Live Booking API](https://verbit.readme.io/docs/live-booking-api), [Verbit Live Sessions](https://verbit.readme.io/docs/live-api), [Verbit WebSocket Connection](https://verbit.readme.io/docs/websocket-protocol).
- **Request encoding.** Booked live sessions can accept multiple media sources, including encoders, web URLs, dial-in, RTMP, Zoom, and other inputs. The docs I reviewed do not publish one universal audio-body encoding for all Verbit speech-to-text surfaces; instead, transport depends on whether you are using post-production jobs, booked live sessions, RTMP, or WebSocket. Sources: [Verbit Live Booking API](https://verbit.readme.io/docs/live-booking-api), [Verbit WebSocket Connection](https://verbit.readme.io/docs/websocket-protocol).
- **Response text path.** This is the least explicit surface in the docs reviewed. The Post-Production API says `/job/get_caption` returns a caption file, `/job/draft` returns draft content, and the API default response format is JSON, but I did not find a single documented JSON text path equivalent to the other providers. Live-session docs describe transcript delivery and downloadable transcription rather than a stable response field path. Sources: [Verbit Post-Production API](https://verbit.readme.io/docs/post-production-api), [Verbit Live Sessions](https://verbit.readme.io/docs/live-api), [Verbit WebSocket Connection](https://verbit.readme.io/docs/websocket-protocol).
- **Credential / settings requirements.** The live auth token is created from a Verbit API key on the platform, and the bearer token expires 24 hours after creation. Booking a session in advance unlocks translations, non-English transcription, ASR settings, and reconnect behavior. Sources: [Verbit Authentication](https://verbit.readme.io/docs/authentication), [Verbit Live Booking API](https://verbit.readme.io/docs/live-booking-api), [Verbit Live Sessions](https://verbit.readme.io/docs/live-api).

## 15. Nuance

- **Auth mechanism.** Nuance Mix ASRaaS uses OAuth 2.0 client credentials with Mix client ID and secret to mint an access token from `https://auth.crt.nuance.com/oauth2/token`; the token is then used as a call credential. The docs also note localized errors can use `Accept-Language` where supported. Sources: [Nuance Authorization Overview](https://docs.nuance.com/mix/tasks/authorize/authentication_overview/), [Nuance Client App Development](https://docs.nuance.com/mix/apis/asr-grpc/v1/client-app-asr/), [Nuance Sample Recognition Client](https://docs.nuance.com/mix/apis/asr-grpc/v1/samples/client-samples-asr/).
- **Base endpoint.** The ASRaaS server host in the sample client is `asr.api.nuance.com:443`. The token endpoint is separate at `https://auth.crt.nuance.com/oauth2/token`. Sources: [Nuance Sample Recognition Client](https://docs.nuance.com/mix/apis/asr-grpc/v1/samples/client-samples-asr/), [Nuance Client App Development](https://docs.nuance.com/mix/apis/asr-grpc/v1/client-app-asr/).
- **Sync / async / stream protocol.** The docs reviewed describe a gRPC streaming recognition client that sends an init message and then audio chunks. I did not find a synchronous HTTP transcription endpoint in the ASRaaS docs reviewed. Sources: [Nuance Client App Development](https://docs.nuance.com/mix/apis/asr-grpc/v1/client-app-asr/), [Nuance Sample Recognition Client](https://docs.nuance.com/mix/apis/asr-grpc/v1/samples/client-samples-asr/).
- **Request encoding.** Requests are gRPC protobuf messages: first `RecognitionInitMessage` / `RecognitionParameters`, then `RecognitionRequest(audio=chunk)` chunks. The sample audio requirements are mono linear PCM, 8 kHz or 16 kHz. Sources: [Nuance Client App Development](https://docs.nuance.com/mix/apis/asr-grpc/v1/client-app-asr/), [Nuance Sample Recognition Client](https://docs.nuance.com/mix/apis/asr-grpc/v1/samples/client-samples-asr/).
- **Response text path.** The client sample prints `message.result.hypotheses[0].formatted_text` for streamed recognition results. The results docs also describe `result_type` and `utterance_detection_mode` controls that influence whether partial or final text is emitted. Sources: [Nuance Results](https://docs.nuance.com/mix/apis/asr-grpc/v1/ref-topics/results-asr/), [Nuance Sample Recognition Client](https://docs.nuance.com/mix/apis/asr-grpc/v1/samples/client-samples-asr/).
- **Credential / settings requirements.** The docs require a Mix client ID and secret, short-lived access tokens, and ASR scope (`scope=asr` in the sample). The sample also says the input audio must match the locale/data pack, and the client may need to change language from `en-US` to region-specific locales such as `fr-CA`, `es-ES`, `en-IN`, or `en-GB`. Sources: [Nuance Authorization Overview](https://docs.nuance.com/mix/tasks/authorize/authentication_overview/), [Nuance Client App Development](https://docs.nuance.com/mix/apis/asr-grpc/v1/client-app-asr/), [Nuance Sample Recognition Client](https://docs.nuance.com/mix/apis/asr-grpc/v1/samples/client-samples-asr/).

## Caveats

- Verbit has the most documentation surface area and the least single-endpoint consistency in the pages reviewed. Its auth and transport vary across post-production, booked live, and ad-hoc live paths.
- Nuance ASRaaS docs are older than the other providers' docs and are heavily Mix-specific; the token and host conventions are documented, but the service model is centered on gRPC streaming rather than a modern JSON REST API.
- For Groq, I only found documented synchronous STT endpoints.
- For Inworld, the STT docs are explicit and internally consistent across sync and WebSocket paths.
