# Kiro CLI Research Notes

Date: 2026-09-02

## Executive Summary

Kiro CLI is Amazon/Kiro's terminal-native surface for the Kiro agentic development platform. The current public documentation describes CLI 3.0 as running the same "unified agent harness" as Kiro IDE and Kiro Web, with shared `.kiro/` project configuration across IDE, CLI, Web, and Mobile surfaces.

## What It Is

Kiro CLI brings AI-assisted development to the terminal for interactive chat, terminal UI workflows, headless automation, voice mode, ACP integration, autocomplete, and code intelligence. The docs position it as the terminal workflow surface for natural-language development tasks such as building, testing, deployment, code review, and custom automation.

CLI 3.0 is a major architectural shift: it uses the unified Kiro agent harness rather than a separate CLI-specific engine. This means improvements to planning, tools, and agent behavior are intended to ship across Kiro IDE, CLI, and Web together, and `.kiro` configuration should be portable across surfaces.

## Installation And Platforms

Documented install command for macOS/Linux/Windows flows:

```bash
curl -fsSL https://cli.kiro.dev/install | bash
```

The installation docs list CLI support for macOS, Windows 11 PowerShell, and Linux with glibc 2.34+ or a musl variant. The fetched install script confirms platform detection for Darwin/Linux, architecture detection for x86_64/aarch64, checksum verification from a manifest, macOS DMG installation into `/Applications`, Linux installation into `~/.local/bin`, and fallback to musl packages when Linux glibc is below the script threshold.

The installer also checks for an existing `q` command and describes Kiro CLI as the new version of Amazon Q CLI. If the installed Q CLI is in an updatable standard path, it attempts `q update`; otherwise it asks the user to uninstall Q CLI and rerun the Kiro installer.

## Licensing And Source Availability

Kiro IDE and Kiro CLI are distributed under a proprietary AWS content license, according to Kiro's license page and CLI marketing FAQ. Kiro Crew is described separately as open source. The public `kirodotdev/Kiro` GitHub repo is useful for public project information and issue tracking, but it is not presented as the source repository for the proprietary Kiro CLI binary.

## Core User Workflows

### Interactive Chat

`kiro-cli` defaults to interactive chat. The command reference says `kiro-cli chat` can start a session, accept a direct prompt, resume previous sessions, resume by ID, open a resume picker, list sessions, list models, set an agent, and set launch-time effort.

Useful examples:

```bash
kiro-cli
kiro-cli chat "How do I list files in Linux?"
kiro-cli chat --resume
kiro-cli chat --resume-id <session-id>
kiro-cli chat --list-sessions
kiro-cli chat --list-models --format json
kiro-cli chat --agent my-agent "Help me with AWS CLI"
kiro-cli chat --effort high "Refactor this module for testability"
```

### Headless / CI

Headless mode uses `kiro-cli chat --no-interactive "prompt"` and is documented for CI/CD tasks such as code reviews, test generation, and troubleshooting build failures. In headless mode, authentication uses `KIRO_API_KEY`; because there is no interactive approval UI, permissions must be granted up front with `--trust-all-tools` or `--trust-tools=...` if tools are needed.

Example pattern:

```bash
export KIRO_API_KEY=ksk_xxxxxxxx
kiro-cli chat --no-interactive --trust-tools=read,grep "Review this PR for security issues"
```

The headless docs also mention `--require-mcp-startup` for pipelines that should fail fast when configured MCP servers cannot connect.

### Spec-Driven Development

Kiro Specs guide work through requirements, design, and implementation tasks. CLI 3.0 adds the Spec agent to the terminal; `/spec new <name>` starts the workflow. Kiro has Feature Specs and Bugfix Specs. Feature Specs support Requirements-First and Design-First variants, plus Quick Spec for generating requirements, design, and tasks in one pass without approval gates.

Spec artifacts are documented as formal requirements, design, and task documents under `.kiro/specs/`. Kiro analyzes `tasks.md`, builds a dependency graph, and runs independent tasks concurrently in waves.

Feature Specs use EARS-style requirements:

```text
WHEN [condition/event]
THE SYSTEM SHALL [expected behavior]
```

### Steering

Steering files are Kiro-specific context for standards and conventions. They support YAML front matter and inclusion modes:

- `always`: loaded into every interaction.
- `fileMatch`: loaded only for matching file patterns.
- `manual`: included on demand via `#name` or slash command.
- `auto`: included when the request matches `name` and `description`.

The docs recommend steering for technology stack, coding conventions, architecture principles, component patterns, testing rules, security policies, and deployment workflow.

### Hooks

Hooks are JSON configs under `.kiro/hooks/`. They run shell commands or inject agent prompts when events occur. Supported on IDE, CLI, and Web for event-driven hooks, shell-command actions, agent-prompt actions, and chat-created hooks.

Documented triggers include:

- `PostFileSave`
- `PostFileCreate`
- `PostFileDelete`
- `PreToolUse`
- `PostToolUse`
- `UserPromptSubmit`
- `SessionStart`
- `Stop`

`PreToolUse` and `UserPromptSubmit` can block execution. Command actions run from the project root and receive session context as JSON on STDIN.

### Permissions

CLI 3.0 moves from broad trust flags and per-tool settings toward capability-based `permissions.yaml`. The migration docs say default behavior without `permissions.yaml` is to prompt or block outside explicit defaults; the new-features page says default allows workspace reads and common read-only commands while denying writes to Kiro settings. Important nuance: older `--trust-all-tools` and `--trust-tools` still exist as session/headless overrides, but `permissions.yaml` is the preferred durable policy surface.

Permissions are capability-oriented rather than raw tool-list-oriented. Docs distinguish tags used to select tools from capabilities used to control what those tools can do at invocation time.

### MCP

Kiro supports MCP across IDE, CLI, and Web for local stdio servers, remote HTTP/SSE servers, JSON config, and server-provided prompts/resources. MCP servers can be configured in workspace/user MCP JSON or inline in agent configuration via `mcpServers`.

The CLI command reference exposes:

```bash
kiro-cli mcp add --name my-server --command "node server.js" --scope workspace
kiro-cli mcp remove --name my-server --scope workspace
kiro-cli mcp list
```

### Skills

Kiro supports Agent Skills. Workspace skills live in `.kiro/skills/`; global skills live in `~/.kiro/skills/`. Skills are progressively disclosed: Kiro loads name/description at startup, activates matching skills by request or slash command, then loads full instructions and supporting assets only as needed.

### Code Intelligence

Kiro CLI has a `code` tool backed by LSP processes. Initialization creates `.kiro/settings/lsp.json`; after first `/code init`, CLI automatically initializes code intelligence on startup when that file exists. Deleting `.kiro/settings/lsp.json` disables auto-initialization; `/code init -f` restarts language servers.

### ACP

Kiro CLI implements Agent Client Protocol via:

```bash
kiro-cli acp
kiro-cli acp --agent my-agent
```

The ACP process communicates over stdin/stdout using JSON-RPC 2.0. Kiro docs describe use from ACP-compatible editors such as JetBrains IDEs and Zed.

### Crew

`kiro-cli crew` launches or forwards arguments to Kiro Crew. On macOS/Linux, CLI prompts to install Crew when missing and accepts `--yes`/`-y` to skip the prompt; on Windows, Crew must be installed separately.

## Commands Worth Knowing

From the command reference:

- `kiro-cli agent`: list/create/edit/validate/migrate/set-default agent configs.
- `kiro-cli chat`: interactive and non-interactive chat, resume/session/model options.
- `kiro-cli translate`: translate natural language to shell commands.
- `kiro-cli doctor`: diagnose installation/config issues.
- `kiro-cli update`: update CLI.
- `kiro-cli theme`: list/set autocomplete dropdown theme.
- `kiro-cli integrations`: install/uninstall/reinstall/status system integrations.
- `kiro-cli settings`: list/get/set/delete/open settings.
- `kiro-cli issue`: create GitHub feedback/bug issue for Kiro.
- `kiro-cli version`: show version/changelog.
- `kiro-cli mcp`: manage MCP servers.
- `kiro-cli acp`: run ACP agent.
- `kiro-cli crew`: launch/pass through to Kiro Crew.

Interactive slash commands include `/help`, `/code`, `/experiment`, `/tangent`, `/todo`, `/issue`, `/logdump`, `/settings`, `/rewind`, `/changelog`, and skill-derived slash commands.

## Authentication, Pricing, Models

Interactive CLI login supports browser/device flows with Builder ID, IAM Identity Center, Google, GitHub, or organization identity providers. Remote machine auth uses a device flow with URL plus one-time code. API key auth is for CI/CD and automation through `KIRO_API_KEY`.

Authentication precedence is documented as:

1. Active browser session from `kiro-cli login`.
2. `KIRO_API_KEY`.
3. No credentials, prompting sign-in.

API keys require a paid Kiro account tier according to the auth docs.

Pricing is shared across Kiro surfaces: there is no separate Kiro CLI price. Public pricing as of 2026-09-02 lists Free with 50 credits, paid tiers Pro ($20/month), Pro+ ($40/month), Pro Max ($100/month), and Power ($200/month), team overages at $0.04/additional credit, and GovCloud around 20% higher with no Free tier.

The models page lists frontier and open-weight models from OpenAI, Anthropic, and others, including GPT-5.6 Sol/Terra/Luna, Claude Opus/Sonnet/Haiku families, DeepSeek, MiniMax, GLM, and Qwen. Costs are credit multipliers relative to Auto. Free tier has limited model access; paid tiers add premium models.

## 3.0 Migration And Caveats

Notable CLI 3.0 changes:

- Same unified agent harness as IDE/Web.
- Built-in Spec agent.
- Capability-based permissions.
- Hooks moved to standalone `.kiro/hooks/*.json`.
- Enhanced Markdown agent config with tools, permissions, MCP servers, resources, and prompt body.
- Tangent side-conversations.
- Session export/import.
- Trusted workspaces.
- Code Intelligence and Knowledge.
- `aws_tool` removed; docs direct AWS access through MCP servers.

Breaking/known gaps:

- V3 session format is not backward-compatible with V2.
- Hooks require migration from embedded config to standalone files.
- Tool IDs changed toward standardized snake_case aliases.
- Legacy non-TUI classic mode does not support the v3 engine.
- CLI 3.0 does not run on Amazon Linux 2.
- Checkpoints are not available in CLI 3.0 and remain IDE-only; session export is the state-preservation alternative.

## Relevance To cmdSpace

Kiro CLI is closest to Codex/Claude Code style terminal-agent tooling, but with a strong repository-local `.kiro/` control plane: steering, specs, hooks, skills, permissions, LSP/code intelligence, MCP, sessions, and custom agents. For cmdSpace, the most relevant ideas to study are:

1. Portable project configuration under one hidden directory.
2. Spec artifacts as durable requirements/design/tasks, not just chat history.
3. Permission policy as declarative capabilities rather than one-off approvals.
4. Event hooks as first-class user/project automation.
5. ACP support as a bridge to editors and agent clients.
6. Headless mode with explicit auth and permission choices for CI.

Integration caution: because Kiro CLI is proprietary and distributed as a binary, cmdSpace should treat it as an external executable/terminal workflow unless Kiro exposes a stable API/protocol for embedding. ACP may be the cleanest protocol-level interoperability path, while shelling out to `kiro-cli chat --no-interactive` is useful for automation but less structured.
